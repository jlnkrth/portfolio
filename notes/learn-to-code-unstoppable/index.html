Principle

You Should Learn How to Code. It Will Make You Unstoppable

Not to become a software engineer. To become the expert who does the automating instead of getting automated.

Last month I watched a task in Asana finish itself. Someone moved a card to a “ready” status, a webhook fired, an agent picked the task up, pulled the client’s context from our wiki, did the work, and posted the result back on the card. Twenty minutes, no editor open, nobody typing.

Here’s the part that matters if you’re not an engineer: the code behind that flow is short and none of it is clever. The valuable part is the checklist inside it — the one a person on our team carries in their head after doing that task five hundred times. The code just holds the checklist still so a machine can run it. Which brings me to the claim in the title: if you’re already an expert at something, learning the basics of code (one free course, a handful of YouTube tutorials) makes you close to unstoppable. And I want to walk you through why, because the reasoning is more concrete than the usual “learn to code” pep talk.

The job description changed

The software engineer of the last decade built apps. Screens and databases. That job still exists, but a new one has appeared next to it, and it pays better relative to the effort: the person who builds AI agents and workflows. The one who can turn an Asana status change into finished work. The one who knows their way around Claude Code plugins, MCP servers, and webhooks, and can wire them into something a whole team runs on.

I do this all day at Masse, and the surprising thing is how little of it is traditional engineering. Most of my time goes into deciding what the agent should know, when it should stop and ask, and where its output should land. That’s judgment work. The code is mostly glue.

Software engineer, last decade Software engineer, next decade
Ships Apps and features Agents and workflows
Core skill Writing a lot of correct code Encoding expert judgment into little code
Typical unit of work A feature behind a ticket An Asana status change that finishes the work itself
Tooling Frameworks, CI, cloud consoles Claude Code plugins, MCP servers, webhooks, skills

Same title, different job. The second column is where the leverage moved.

Your expertise is the scarce part

Everyone has the same models now. You and your competitor both talk to the same Claude, the same GPT. So the model can’t be the edge. The edge is what you feed it: the SOPs, the taste, the pricing instincts, the “we tried that in 2023 and it burned us” scar tissue that only exists in the heads of people who’ve done the work for years.

An agent without that knowledge produces generic output at incredible speed, which is worse than useless. An agent with it produces your best person’s first draft, on demand, for every teammate. The whole game is getting the knowledge out of the head and into files the agent reads. In practice, expert knowledge maps onto agent infrastructure like this:

your SOPs and checklists[ become skills the agent runs ]
your taste and thresholds[ become rules in a prompt or config ]
your client and domain context[ becomes wiki pages the agent reads ]
your “stop and ask a human” instincts[ become hooks and escalation rules ]

Nothing on the left requires an engineering degree. Everything on the right requires knowing basic code.

And here’s the catch that makes coding basics non-optional: the person doing this translation has to be able to read what the AI writes. Models will happily generate the glue code for you. But if you can’t read it, you can’t tell whether the agent checks the threshold you meant or a threshold it invented. I wrote about this in the memory management piece: the rules are simple, but someone has to be able to verify the agent actually follows them.

Learn less than you think

Now the good news. The bar is much lower than “become a programmer.” You need enough code that code stops being scary. That’s roughly Harvard’s CS50, which is free, plus a few evenings of YouTube on the specific plumbing agents run on. You can skip almost everything a professional engineer had to learn, the frameworks and the leetcode puzzles. None of that shows up in agent work.

Here’s the actual syllabus I’d hand a smart non-engineer on our team. Copy it, it’s the whole plan: 

The expert's coding syllabus

1. CS50x (free, self-paced) — do weeks 0–7 properly, skim the rest.
   You want: variables, functions, loops, and enough Python to read a script.
2. One YouTube tutorial on APIs and JSON — what a request is, what a response is.
3. One YouTube tutorial on webhooks — how an Asana status change becomes an event.
4. One YouTube tutorial on git — clone, commit, push, pull request. Nothing more.
5. Install Claude Code and let it write everything. Your job is reading, not writing.

Stop when you can read a 100-line script and say what it does. That's the bar.

The bar is reading fluency, not writing fluency. AI handles the writing.

Honest caveat: this will not make you employable as a software engineer. Hiring interviews and million-line codebases are a different world, and pretending otherwise is how “learn to code” advice got a bad name. But you’re not trying to compete with engineers. You’re trying to combine: your ten years of domain expertise plus their entry-level plumbing skills. An engineer can’t copy your ten years. You can copy their first three months.

Wire one workflow end to end

Everything clicks the first time you connect a real trigger to a real result. My standard recommendation: take the task you’ve done so often you could do it asleep, and wire this exact flow around it.

Look at what’s actually in that diagram. One webhook. One agent run. A wiki page holding your SOP. An if-statement holding your quality bar. That’s CS50-week-one material plus two YouTube tutorials, and it’s the same shape as the flows we run in production at Masse. All the sophistication lives in the checklist, and you already own the checklist.

Once one flow works, the rest is repetition. Package your prompts and commands so teammates get them too (that’s what Claude Code plugins are for). Add a second trigger. Encode another SOP. Every workflow you ship compounds, because the wiki pages and skills you wrote for the first one feed all the others.

So no, don’t learn to code to change careers. Learn to code because you’re already an expert, and a few weeks of basics is all that separates your expertise from an agent that works while you sleep. The expert who can code doesn’t get automated. They do the automating.
