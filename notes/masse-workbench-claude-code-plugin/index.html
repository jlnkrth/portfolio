Case study

We Packed Our Whole Agency Into a Claude Code Plugin

Fifty people, one install command. What Claude Code plugins actually are, and a tour of the Masse Workbench.

For most of last year, “setting up Claude Code” at Masse meant a Slack DM to me. I’d send someone a zip of prompt files, a JSON snippet for the MCP servers, and a fifteen-minute Loom. Two weeks later their setup had drifted from everyone else’s, and the agent that worked great on my machine gave them mediocre output. With 50+ people across the world, I was the bottleneck and the bug.

The fix was to stop distributing our setup as advice and start distributing it as software. Everything we know about running agents at Masse now lives in one Claude Code plugin, the Masse Workbench, and installing it takes one command. This piece explains what a plugin actually is, what we put in ours, and what changed when “how we work” became a versioned artifact instead of tribal knowledge.

Failure mode

The hand-rolled era failed quietly, the way config drift always does. Nothing crashed. Output just got inconsistent, and nobody could say why, because no two machines were running the same instructions.

Symptom Cause
Same task, wildly different agent output per person Everyone’s CLAUDE.md was a personal fork of a fork
“The agent can’t see Asana” tickets every week MCP config pasted by hand, keys and paths wrong in new ways each time
Prompt improvements never reached the team Fixes lived on the fixer’s machine; there was no update channel
Onboarding a new hire took a call with me The setup existed as a person, not as a package

Config drift never pages you. It just quietly makes everyone slightly worse.

What a plugin actually is

Claude Code plugins solve exactly this. A plugin is a folder in a git repo with a manifest at .claude-plugin/plugin.json, and it can carry five kinds of cargo: slash commands, subagents, skills, hooks, and MCP server configs. Whatever the plugin ships shows up in every installer’s Claude Code as if they’d written it themselves.

.claude-plugin/plugin.json[ name, version, author ]
commands/[ slash commands, one .md each ]
agents/[ subagents with their own prompts ]
skills/[ SOPs the agent loads on demand ]
hooks/[ scripts that run on agent events ]
.mcp.json[ MCP servers, preconfigured ]

The whole format is folders of markdown and JSON. If you can write an SOP, you can write a plugin.

Distribution runs through marketplaces, which sounds grander than it is: a marketplace is just another git repo with a .claude-plugin/marketplace.json listing plugins. Ours is private. A new teammate adds it once, then installs:

/plugin install masse-workbench@masse

Copy includes the marketplace add. That command replaced my fifteen-minute Loom.

The manifest is small enough to read in full. This is the entire contract between the plugin and Claude Code: 

{
  "name": "masse-workbench",
  "description": "Masse's commands, skills, and MCP servers for Claude Code",
  "version": "1.4.0",
  "author": { "name": "Masse" }
}

Everything else is convention: Claude Code discovers the folders next to the manifest.

Inside the workbench

The workbench carries three layers, and each one replaced something we used to distribute by hand.

Commands are the entry points. They’re namespaced by plugin, so the team gets /masse:brief to turn a client page from the wiki into a working brief, /masse:audit to run a search performance pass, and /masse:handoff to package a thread’s state for the next person. Each command is a markdown file. When someone improves a prompt, that’s a pull request, and the whole team gets it in the next version.

Skills are where the SOPs went. The checklists our senior people carried in their heads are now files the agent loads when the task calls for them, written in the same stop-and-classify style as our memory rules. This is the layer that took real work, because writing down what an expert actually does is harder than any of the plumbing.

MCP servers are the hands. The plugin ships preconfigured connections to Asana, to our wiki, and to Search Console through gsc-mcp-server, so nobody pastes JSON configs anymore. Install the plugin and the agent can already see the tools it needs.

What changed

Setup stopped being a conversation. A new hire runs two commands and has the same working environment as the person who’s been here three years, which killed the “works on my machine” class of prompt bugs outright.

Improvements started compounding instead of scattering. Before, a better prompt died on the machine of whoever wrote it. Now every fix is a commit, every release is a version bump, and /plugin update ships it to everyone. We review prompt changes the way we review code, because they finally live where code lives.

And the plugin became our onboarding document without meaning to. When someone asks how we run an audit, the honest answer is “read the skill file.” The workbench is the current, executable version of how Masse works, and it can never drift from practice, because it is the practice.

The lesson generalizes past Claude Code. Any knowledge your team distributes as advice will drift; knowledge distributed as a versioned package stays true. If your best practices live in people’s heads and Looms, put them in a plugin. It’s folders of markdown. You already know how to write those.
