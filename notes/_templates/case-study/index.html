Case study

We Replaced Our Dashboard with a Text File

The bet: a status page nobody maintains is worse than no status page.

We spent four months building a metrics dashboard, and six months watching nobody open it. Charts for everything, filters for everything, and a team that still asked “how are we doing?” in standup every morning.

So we deleted it. In its place we put a single text file, status.md, updated by a script every morning at seven. The file answers three questions and nothing else: what changed, what broke, what needs a decision.

Failure mode

The dashboard failed the way most dashboards fail — quietly. It never went down. It just stopped being read, because reading it was work: pick a date range, pick a segment, remember what last week's number was. People wanted an answer, and we had given them a tool for finding answers. Those are not the same product.

Symptom Cause
“How are we doing?” asked daily in standup Dashboard shows data, not answers — reading it takes effort
Charts silently wrong for three weeks Nobody looked; a broken query looks the same as a slow month
Every question spawns a filter request Tool invites exploration instead of settling the question

Name the failure pattern before explaining your fix.

The approach

We stopped optimizing for what people could look up and started optimizing for what they would actually read. A text file in the repo is the lowest-friction surface we have: it shows up in the editor, in pull requests, and in Slack when the bot posts it each morning.

The bet: nobody reads a dashboard, but everybody reads three sentences that arrive by themselves.

Architecture

Three sections, fixed order, so the file reads the same every day:

what changed[ deltas past threshold ]
what broke[ failed checks, empty if none ]
needs a decision[ human-added only ]

Fixed section order makes daily status scannable under 30 seconds.

thresholds:
  signups_weekly: ±15%
  churn_monthly: ±0.5pp
  error_rate: > 1%
rule: below threshold → not in the file

Thresholds convert taste into explicit publishing rules.

The thresholds are the real product. They encode what “worth mentioning” means, in a file anyone can challenge in a pull request.

What changed

Standup stopped opening with a status question, because everyone had read the same three sentences an hour earlier. When a number broke, we knew that day — the broken-query problem disappeared, since a script that fails to write the file fails loudly. And the “needs a decision” section became the queue that feeds our decision log.

Use one metric to prove adoption, not five metrics to look sophisticated.

The lesson generalizes past dashboards. When a tool isn't used, the instinct is to make it more capable. Usually the opposite is true: make it smaller, make it arrive on its own, and make it say less.
